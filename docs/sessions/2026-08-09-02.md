## 2. Loop 2 — the audit spine's missing emitters (ADR-48)

M1's standing promise is "every mutating action emits an audit event". Six paths
did not. Five were unremarkable. The sixth was not: **refresh-token reuse
detection revokes an entire sign-in family because it believes the token was
stolen, and wrote nothing at all.** That is the single event a security review
is most likely to come looking for, and the answer to "has this ever happened
here?" was an empty table with no way to tell *never* from *not recorded*.

### Now emitted

| Action | Where | The point |
|---|---|---|
| `auth:refresh_reuse` | `services/auth_sessions` | Committed in the same transaction as the revocation. Attributed to the user **and their org** — a NULL org is invisible in the only screen anyone would look at. |
| `backlink:competitor_track` / `_untrack` | backlink routes | Tracking a competitor is what causes their profile to be pulled: a spending decision. |
| `checker:submit` | `POST /checker` | The only path that spends vendor money for somebody with no account. `cache_hit` separates an LLM bill from a database read. |
| `checker:lead`, `waitlist:signup` | routes.py | Recorded **without the address**. |
| `billing:quota_denied` | `services/quota` | A 429. Not a mutation. Audited anyway. |

### Three decisions, each with a reasonable-looking wrong answer

**The rule changed, and that is the substantive outcome.** "Every mutating
action" is not keepable: a successful refresh rotation *is* a mutation, fires
roughly four times an hour per signed-in device, and auditing it would out-write
the entire Admin Panel's yearly output in a week. An audit log is read by a
person; a record nobody can find is not a record.

So the rule is now **every mutation with a consequence emits, and every
deliberate silence has a test asserting the silence.** The second half is
load-bearing. An intentional gap nobody tested is indistinguishable from a
forgotten one — which is precisely how five unaudited paths survived four
sessions. Four silences are now pinned: successful rotation, ordinary expired
refresh, duplicate waitlist signup, kill-switched checker submit.

**An append-only table must not hold erasable PII.** `audit_events` cannot be
updated or deleted through the application — migration 0018's triggers — so
anything written there is *permanent*. Copying an email into `checker:lead` or
`waitlist:signup` would have put the erasure path this milestone still owes into
direct conflict with the integrity guarantee: honouring a deletion request would
mean breaking the triggers or lying. Those events store the **reference** and
drop the **value**. Erase the submission and the row still truthfully says an
address was attached, and no longer says whose.

Failed logins stay the deliberate exception, and the distinction is principled:
there the attempted address *is* the evidence, and no other row carries it.
Where the value lives elsewhere and is erasable, the trail points at it; where
the value is the finding, the trail keeps it.

**A refusal is worth auditing even though nothing mutated.** ADR-45 made every
organization Free by default, which makes a refusal the likeliest thing to
happen to a live user — and "my analysis just fails, why?" had an answer in no
log, no forwardable response body, and no screen. This is not a new pattern: the
permission gate has committed its own 403 event since P7.2, and `services/auth`
commits a failed login the same way. Three refusal classes now behave
identically.

`billing:quota_denied` commits its own transaction because the request is
already unwinding — the route raises, the handler answers 429, the session
closes uncommitted, so an event merely *added* to it would be discarded along
with the refusal it describes. That is safe **only** because the quota check
raises before it writes and every route runs its quota gate before any other
mutation. Asserted by a test, not assumed.

### Two things a reviewer will notice

`backlinks.untrack_competitor` returns the removed domain instead of `True`.
After the delete there is nothing left to read, and a removal event that cannot
name what was removed answers a weaker question than the one it exists for —
the same reasoning as `/auth/logout` resolving its user before spending the
token. Still falsy on not-found.

The reuse event's detail key is `revoked_family`, **not** `family_id` or
`session_id`. `redact()` blanks any payload key containing "session", so the
obvious names would have stored `[redacted]` and lost the one field saying which
sign-in was killed. A test pins the name.

### Rejected

Emitting the refusal from the exception handler in `api.main`. It has the
request but not the caller's organization, and the request-scoped session is
already gone — so it would need a second session, which **the test harness
cannot express**: a `StaticPool` in-memory SQLite shares one connection, so a
"separate" session would share the transaction and behave differently in tests
than in production. A gate whose audit trail is untestable is not a gate.

## 3. Loop 3 — the history screen `org_id` had no reader (ADR-49)

P7.6 gave `analyses` an `org_id`. Nothing read it. The only route back to a
result was still the URL a submitter happened to be redirected to, so closing
the tab lost the run — which had been true before too, but was then at least
*consistent* with runs belonging to nobody. After P7.6 the data said the run had
an owner and the product offered that owner no way in (tech-debt #77).

`GET /api/v1/analyses` (signed-in, org-scoped, paged, status filter), the
`/analyses` screen, and a "Your analyses" nav entry under AI Visibility.

**The decision worth recording is not "we added a list."** It is that this route
is authenticated while its sibling `GET /analyses/{id}` is not. A capability URL
works because knowing the unguessable id *is* the authorization; a list has no
id to know, so there is no capability a caller could present and the only
coherent answer to "whose analyses?" is the caller's organization. An
unauthenticated version could only ever mean "everyone's" — not a weaker version
of the feature but a different and much worse one.

Stated as a rule for the routes M3–M6 will add: **a route keyed by an
unguessable id may be a capability; a route that enumerates never can be.**

**It is also the first application call site of `tenancy.scoped()`.** That
helper has existed since P7.1 with zero callers — the fail-closed seam that
ADR-35, `architecture-target.md` and the P7.1 card all described as shipped, and
that tech-debt #63 recorded as fiction. Used here for the property it exists
for: an org-less context **raises** rather than quietly returning every tenant's
rows, which the tests pin. **This does not close #63** — one call site is not a
guarantee, and the A9 leakage suite is what makes tenancy enforced rather than
remembered — but the seam is no longer theoretical and now has a worked example.

Three things in the list that are easy to get wrong, all tested:

- **A missing score renders as an em dash, never a zero.** A queued run has not
  been measured; a run that scored zero is a much worse and entirely different
  fact. Rendering `null` as `0` tells a customer their brand is invisible in AI
  answers when the truth is nobody has looked. Asserted in both directions — a
  genuine `0.0` still renders as `0.0`.
- **Summary rows carry no `result` envelope.** A finished run holds dozens of
  responses; a twenty-row page of full envelopes is thousands of records to draw
  a table of URLs and scores. A separate flat schema, not `AnalysisOut` minus
  fields, so a field added to the detail view cannot silently make the list
  twenty times heavier.
- **The sort has an id tiebreaker.** Runs submitted in one transaction share a
  timestamp, which is exactly when page 2 repeats a row from page 1 and drops
  another — and a customer hunting the run that went missing would never find it.

Pre-P7.6 runs and anonymous checker runs appear in nobody's history: the first
belong to no tenant (inventing an owner would be a guess written into a
customer-facing screen), the second are excluded twice over — no `org_id`, and
`kind` outside `LISTABLE_KINDS`.

**Deliberately not done:** an index on `analyses(org_id, created_at)`. It is a
migration, and migration-bearing work is gated on operator item B13. Free at 57
rows; recorded as tech-debt #87 with the instruction to ride along with the next
migration rather than be discovered under load.

## 5. Assumptions recorded

- **`checker:submit` is audited on cache hits as well as misses**, so "every
  mutating path emits" stays literally true (a hit still writes a submission
  row) and `cache_hit` is what tells the two apart. If the checker ever goes
  live at volume it becomes the highest-volume writer into the append-only
  table — tech-debt #86, revisit at `public-checker-go-live`, not before.
- **`quota.consume(context=…)` is optional**, so the money layer stays callable
  from a worker or a script with no user. Every current call site passes it.
  Nothing enforces that (tech-debt #85).
- **`LISTABLE_KINDS = ("mvp",)`** — a future analysis kind must be added
  deliberately rather than appear in someone's history because it happened to be
  persisted in the same table.
- **The history screen does not poll.** It is a way *back* to a run, and the row
  links to the page that does poll (tech-debt #88). Wrong the moment it becomes
  the first thing a user sees after submitting.

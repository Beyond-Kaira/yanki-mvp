## 2. What was built

### 2.1 Invitations, end to end (ADR-37)

New `invitations` table (migration 0018), `services/invitations.py`,
`api/invitation_routes.py`, and two screens. The decisions worth recording:

- **The token is never stored** — a SHA-256 is, exactly as `auth_sessions`
  treats refresh tokens. Plain SHA-256 rather than a password hash because the
  value carries 256 bits of CSPRNG entropy: there is nothing for a slow hash to
  defend, and an Argon2 verify on a public unauthenticated endpoint is a
  denial-of-service surface.
- **The failures are specific**, which is the opposite of what this codebase
  does everywhere else. A cross-org member id answers 404 precisely so it
  cannot be used to enumerate accounts; an invitation answers *expired* /
  *withdrawn* / *already used* / *not valid* distinctly, because a 256-bit
  token is not enumerable and telling somebody holding a real link "this
  expired on Tuesday" is the difference between a recoverable moment and a dead
  end.
- **Expiry is derived, never stored.** A status column would need a sweeper and
  would be wrong between runs.
- **The invited address is authoritative** — there is no field to override it,
  or an invitation to alice@ would be a way to create an account as bob@ with
  alice's granted role.
- **An existing account must sign in before accepting.** Accepting anonymously
  with a *new* password would be an account takeover by anyone who intercepted
  the link.
- **Email honesty.** `emails_enabled` defaults False in every environment, so
  the create response reports `email_sent: false` and hands back the link
  rather than claiming a send that never happened. The Admin Panel shows it,
  once.

### 2.2 The audit trail became usable as evidence (ADR-38, ADR-39)

Three separate gaps, each of which made the trail weaker than it looked:

1. **Request identity was never captured.** `RequestContextMiddleware` now sets
   a `ContextVar` that `audit.emit` reads as a default, so every pre-existing
   call site gained request id, hashed IP and user agent without being
   rewritten. `ContextVar` and not a thread-local, because Starlette may resume
   a coroutine on a different worker thread; reset in a `finally`, without
   which a pooled task attributes the next request to the previous caller's IP.
2. **Auth events belonged to no organization.** `audit_events` is queried *by
   org*, so a login written with `org_id = NULL` was a sign-in trail nobody
   could read. Signup and login are now attributed — including a failed login
   for a *known* address, since "somebody is guessing at my colleague's
   password" is exactly the event an administrator needs to find. An unknown
   address stays NULL, because it genuinely belongs to no tenant.
3. **Tamper resistance was a convention.** Now: a per-row SHA-256 of the row's
   own content, plus a Postgres trigger that raises on UPDATE or DELETE
   (`FOR EACH ROW`, so a `DELETE FROM audit_events` with no `WHERE` fails too).

   **A hash chain was rejected on concurrency grounds, not effort.** A chain
   also detects deletion, but computing one means reading and locking the chain
   head on every write — serializing every audited request in the application
   behind one row. Deletion is prevented at the database instead of detected
   after the fact. The residual is stated in the code: a superuser who drops
   the trigger first is not detectable, and closing that needs an external
   append-only sink (M8, not promised here).

Verification reports **three** verdicts, not two: `ok`, `altered`, and
`unverifiable` for rows written before the column existed. Back-filling those
would manufacture evidence; reporting them altered would cry wolf; reporting
them intact would be a claim the data cannot support.

Then the query surface the requirement actually asked for: filter (action
prefix, actor, entity type, entity id, outcome, date range), search, sort
across five columns, pagination with a true total, and per-record history.

**One subtle bug fixed in the design rather than found later:** the sort always
ends with `id` as a tiebreaker. Events written inside one transaction share a
timestamp to microsecond precision often enough that without it page 2 repeats
a row from page 1 and skips another — an ordinary annoyance in a product list
and a serious one in a log somebody is reading to prove a negative. There is a
test that walks four pages and asserts no id appears twice.

### 2.3 Role management completed

`DELETE /api/v1/admin/members/{id}` removes the **membership**, never the user.
Two different things get confused whenever a product offers one button for
both: the person may hold seats in other organizations, and their authored rows
— analyses, audits, the audit trail itself — must survive their departure or
the history becomes unreadable. Guarded exactly like a role change (last owner,
self), audited with the role that was lost, and it asks for confirmation in the
UI because it is the only irreversible action on that screen.

### 2.4 The rename, done properly

`/admin` is now a **top-level nav section** called **Admin Panel** with three
tabs, not a leaf under Settings. Governance is a different job done by a
different person from "change my password", and burying it one level down under
a personal-preferences heading is how a governance surface becomes invisible to
the person who needs it. Breadcrumb, `<h1>`, nav label, flyout title, section
routing and the Settings cross-link all say Admin Panel.

A real bug fell out of the nav test: `flyoutItemActive` matched by subtree, so
`/admin` (Members) lit up while you were reading `/admin/audit`. Fixed with an
exact-match set that already existed for the two visibility overviews.

### 2.5 CI (ADR-40)

- A **formatting gate scoped to changed files**. Repo-wide is impossible today
  — ~47 backend files on `main` predate any format gate (tech-debt #57) — and
  the two repo-wide outcomes are both bad: red CI on every unrelated PR, or a
  reformat-the-world commit that buries every diff after it. Scoped means the
  unformatted set can only shrink. The residual sweep stays open and is now
  described accurately in #57 rather than as "not done".
- **Named gates** so a red check says which promise broke: migrations
  (up/drift/down) + the append-only trigger; authorization rules; Admin Panel
  API. A generic "pytest failed" on a governance surface is the difference
  between a five-minute fix and a bisect.
- e2e now runs **journeys** and the **viewport matrix**, not only the happy
  path — and the stack gets `PUBLIC_BASE_URL`, without which invitation links
  would be built from a default that happens to be right.

## 5. Assumptions and residuals, recorded rather than buried

- **`audit.emit` still swallows its own errors** — right at the request level
  (a failed audit write must not turn a successful password change into a 500)
  and wrong at the completeness level. The trail is tamper-evident but not
  loss-evident. New **tech-debt #59**; the fix is an outbox and belongs to A9.
- **Workspace-scoped roles are honoured at org grain.** The role strings exist
  and `invitations.workspace_id` is written, but `workspace_grants` was never
  built, so an Editor in a three-workspace agency is an Editor in all three.
  Safe, but not the model §5 of the plan promises. New **tech-debt #60**.
- **The organization profile is read-only** — no PATCH, so a personal org keeps
  its generated name forever. `ORG_UPDATE` is already defined and granted. New
  **tech-debt #61**.
- Invitation emails go nowhere until the operator sets `EMAILS_ENABLED=1` and a
  verified `EMAIL_FROM`. The API says so honestly and the panel shows the link,
  so the feature is usable in the meantime — but the operator should know.
- **`PUBLIC_BASE_URL` must be set in production.** It is the one value the API
  cannot infer from the request that carries it, and every invitation link is
  built from it. Recorded as an operator item.

# Indexed sector lookup build plan

Branch: `feat/industry-sector-index`, based on `feat/top-cited-pages`.

The report will fetch only records matching the selected normalized sector at
the SQL level. Original sector labels and citation ranking semantics remain
unchanged. No semantic synonym mapping or precomputed score totals are added.

1. Schema foundation: shared spelling normalizer, nullable indexed `sector_key`,
   and an Alembic-autogenerated schema migration. Backfill is a separate command.
2. Writer integration: populate the key on new records and keep sector updates
   consistent; inspect all supported write paths.
3. Reader integration: filter ranking by `sector_key` in SQL and group the sector
   catalog by that same key. Preserve evidence checks and output contracts.
4. Verification: compare ranking results, exercise PostgreSQL migrations and
   inspect the query plan on an isolated database before local application rollout.

Each step is reviewed with the user before advancing. Apply the migration before
starting the updated application, with GEO writers stopped until the matching
writer code is deployed. Run the separate backfill before switching to indexed
readers. Unknown live provenance stays unknown.
The migration's regular index build and backfill require a maintenance window
assessment for large production datasets. Downgrade removes only the derived
column/index, preserving original sector labels and GEO evidence.

No application database migration, push, or PR update is part of step 1.

## Steps 1–2 review checkpoint

Implemented the shared normalizer and reused it in the existing ranking module;
added the model column/index and autogenerated migration `0026`. The earlier
handwritten migration was replaced at the user's request. Alembic generated
only the column and index from the model against an isolated PostgreSQL database
built through revision 0025. Upgrade, downgrade, re-upgrade and `alembic check`
passed on that database.

The ORM derives `sector_key` whenever `sector` is assigned, including through
the existing `geo_record_from_audit` writer and subsequent ORM edits. Direct SQL
or bulk writes bypass this hook and must supply the derived key explicitly.
No other application GEO insertion or sector-update path was found.

Backfill (run from backend after migration):

```sh
python -m app.services.backfill_geo_sectors
python -m app.services.backfill_geo_sectors --apply
```

Default is preview only. The apply command fills missing nonblank keys in
500-row keyset batches, preserves existing keys and original labels, and checks
that a row's sector/key has not changed concurrently before updating it. All
updates are in one transaction; failure rolls back and the command is repeatable.
For a race with a legacy writer, rerun after stopping/updating that writer.

The application database has not been migrated. This is an intermediate code
checkpoint: the updated ORM expects the new column, so do not treat this branch
as ready to run against the old database schema. SQL reader integration and
query-plan verification await the user's next-step review.

## Step 3 review checkpoint

The sector catalog now groups and orders `geo_records.sector_key` directly in
SQL. Ranking adds `WHERE geo_records.sector_key = :sector_key` before streaming
joined GEO/response/analysis rows, so unrelated industries do not enter Python.
The authenticated API paths and response schemas are unchanged:

- `GET /api/v1/industry-citations/sectors`
- `GET /api/v1/industry-citations/ranking?sector=...`

A focused regression test captures the executed ranking SELECT and requires the
database predicate, preventing a future refactor from silently restoring the
full-table application-side filter.

## Step 4 verification checkpoint

The autogenerated migration was applied to the local development database with
the API, worker and audit worker stopped. Backfill preview reported 178 rows;
apply updated 178; the next preview reported zero, proving the operation is
repeatable. Services were restarted after validation.

Results before and after indexed filtering match:

- sector catalog: artificial intelligence 60, e-commerce 99, financial technology 19;
- e-commerce: 99 candidates, 30 eligible answers, 10 distinct questions,
  34 sites and 36 pages.

PostgreSQL chooses a sequential scan for the current 180-row table because it is
cheaper at this size. With sequential scans disabled for diagnostic purposes,
`EXPLAIN` uses `Bitmap Index Scan on ix_geo_records_sector_key` with the expected
condition, confirming that the index is usable as the table grows.

The migration chain passed four PostgreSQL tests: clean upgrade, schema/model
drift check, full downgrade and seeded catalog. The isolated database created
for generation and verification was removed afterward. The local application
database contains a pre-existing `geo_records_legacy_metadata` table that is not
declared by any current model or migration; local `alembic check` reports it as
an unrelated removable-table drift. This work did not alter that table.

Focused validation: 49 ranking/writer/API tests plus four PostgreSQL migration
tests passed. Ruff, mypy and whitespace checks passed.

Final backend validation: the complete suite passed with 1,274 tests and 22
environment-dependent skips. The first sandboxed run produced 54 DNS-dependent
SSRF/discovery failures because `example.com` could not be resolved as public;
rerunning the same suite with normal DNS removed every failure. Ruff checked the
full app/tests tree, mypy checked all 141 application source files, and the
whitespace check passed.

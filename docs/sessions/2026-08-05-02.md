### 1.5 A loaded gun found on the way in — repaid before P7.1 touched it

P7.1's deliverable is a migration, so the first thing checked was whether the
migration chain is currently sound. It was not. Against a clean, fully-migrated
Postgres, **`alembic check` failed**: eight indexes exist in the migrations and
in production, but were never declared on `Base.metadata` —

| table | migration-only index |
|---|---|
| `analyses` | `ix_analyses_status_created`, `ix_analyses_checker_reuse` |
| `serp_checks` | `ix_serp_checks_analysis_id` |
| `seo_checks` | `ix_seo_checks_analysis_id`, `ix_seo_checks_check_id_status` |
| `checker_submissions` | `ix_checker_submissions_analysis_id` |
| `site_audits` | `ix_site_audits_project_created_at`, `ix_site_audits_queue` |

Autogenerate compares a live database against the **models**, so an index that
lives only in a migration reads as one the models want *dropped*. The next
routine `alembic revision --autogenerate` — precisely what P7.1 calls for —
would have emitted eight `op.drop_index(...)` calls, and merging that
auto-deploys. The two that would have hurt most are the site-audit queue index
and the checker 24h-reuse index. Nothing caught it because every test builds
its schema with `Base.metadata.create_all`: the models were the only definition
under test, so test databases and production had quietly different schemas.

Repaid in `aa0c80c`, additively: the eight are declared on the models. **No
migration changed and no production DDL runs** — the indexes already exist
there; what changed is that the models now admit it, and SQLite test databases
now build the same shape production has. `alembic check` is clean.

A guard came with it — `backend/tests/test_migrations.py`, the first test in
this repo to exercise the migration chain at all: `upgrade head` from empty
builds exactly `Base.metadata`'s tables; `alembic check` finds no drift;
`downgrade base` reverses the whole chain (ADR-30's rollback concern, one layer
lower). Postgres-only, skipped when `TEST_DATABASE_URL` is unset, so the
default `uv run pytest` stays hermetic. Suite: **488 → 491 backend**.

One incidental change rode along: `ruff format` collapsed a `GeoRecord` line
that PR #11 left unformatted. That the file could sit unformatted on `main` at
all is its own finding — CI gates `ruff check` but never `ruff format --check`
— recorded as tech-debt **#57** with the fix deliberately left to its own PR.

### 3.1 Three defects found and fixed that nobody had asked for

1. **Eight indexes existed only in migrations** (`aa0c80c`). `alembic check`

   tech-debt #54, as the resume prompt asked. Writing it is what surfaced

## 7a. Post-merge verification (added at close, after PR #27 and #28 shipped)

The session did not end at "tests pass". Everything below was checked against
the deployed build.

**Testing added because the existing tests proved the wrong thing.** Every
other test of this milestone calls a service function directly.
`get_org_project()` returning `None` for a stranger is not the same claim as
"a real signed-in HTTP request for another tenant's project gets a 404" —
between them sit the bearer token, `get_current_user`, `get_org_context`, the
membership lookup and the route's error handling. So
`tests/test_admin_panel_e2e.py` (28 tests) signs up, logs in, and carries real
issued tokens with nothing overridden. It found a real bug on the way: **an
owner whose membership row vanished was locked out of their own organization**,
because `provision_personal_org` returned the existing org without restoring
the missing membership. Fixed — a *missing* row is repaired, a *deactivated*
one is left alone, and both directions are now asserted, because healing a
half-failed signup and reviving a revoked member look almost identical.

**A live stack, not just a test harness.** A real uvicorn against a real
Postgres at migration head: signup → login → project create → cross-tenant 404
→ scoped listings → forged `X-Org-Id` 403 → anonymous submit/read → waitlist.
All passed. Then the backlink engine driven through five real import cycles on
Postgres, reproducing the whole delta sequence — 8 new, then 2 new / 0 lost
(one miss is provisional), then 1 lost (second miss confirms), then 1
**regained** (not a second birth), then a truncated pull that claimed **zero**
losses. Toxicity flagged exactly the seeded `/24` link farm; authority
components summed to the score shown; 5 quota units consumed with 6 ledger
rows (1 grant + 5 `$0` settles, each *written* rather than skipped).

**Rebased onto `main` before merging**, linear history, content verified
byte-identical to pre-rebase, full suite re-run, CI 8/8 green.

**Merged with the owner's admin bypass, stated plainly.** The base ruleset
requires one approving review and GitHub does not permit self-approval; with
no second reviewer available the only path was the bypass, on the operator's
explicit instruction. It is recorded here because a merge that skipped the
repo's own review gate should be visible in the log, not only in the reflog.

**Two deploys, both verified.** `6c55019` then `6e779e1`; `.last-good`
recorded, containers healthy, migrations at `0016_seed_plans`, all eight
co-tenant containers undisturbed, no errors in api or worker logs.

**One real defect found by inspecting production after the first deploy:**
`plans` had **zero rows**. 0015 created the table and `seed_plans()` was never
called at deploy time. Not visible yet — nothing on a live path consults a
quota, since backlinks ship dark — but a trap for whoever wires the first one,
because `limit_for()` falls back to Free and with no Free row to fall back
*to* it returns 0, refusing everything. Fixed by migration **0016** (PR #28),
seeded in a migration rather than a startup hook so it runs once per database
with no race between booting containers.

That fix then failed CI's migration gate, **correctly**: the gate asserts that
`downgrade -1` changes something, and a data-only migration changes no DDL.
The response was to strengthen the gate rather than exempt the migration — its
snapshot now includes per-table **row counts**, which makes data-only
migrations checkable by the same property *and* makes the round-trip catch a
non-idempotent upgrade, a class of bug this repo has already produced once and
never tested for. Verified three ways: 0016 passes, the schema-changing 0015
still passes, and a deliberately injected row is caught by name.

**The pipeline itself, proven on the deployed build.** One live analysis on
production completed end-to-end (`done`, geo_score 45.5, 10 responses) — the
check the operator's own docs define. It also settled the cost question
exactly: the `measured` engine has 70 responses across 7 analyses and a total
recorded cost of **$0.092207**, which is precisely the single run made on the
fixed build. **The other six measured analyses recorded $0.00.** The old panel
engines recorded cost correctly, which is why analysis-level totals looked
non-zero and hid the gap for a week.

## 2. The card was blocked by something no document mentioned

`enforce-quota-on-spend-paths` reads like a wiring job: `services/billing` has
`check_quota`, `consume_quota`, `reserve`, `settle`; three routes need to call
them. Reading the code first — the standing instruction, earning its place a
fifth time — found the actual blocker.

**`POST /api/v1/analyses` took no authentication.** Not a permission gap, not a
weak check: no credential of any kind. Which meant:

- every analysis a paying customer ran carried `org_id = NULL`;
- it belonged to no organization, appeared in no organization's history, and
  could be metered against **nothing**;
- anyone could spend money at a paid vendor through it, bounded only by the
  per-IP rate limit.

It is a leftover, not a decision. `/` used to *be* the analysis form; session 21
made `/` a landing page and moved the form behind sign-in, and nobody closed the
route the form posts to. The evidence that closing it breaks nothing is
mechanical: every caller of `createAnalysis` sits inside `RequireAuth`
(`/dashboard`, `/ai-visibility`, `/search-visibility`, the analysis-bound
subpages), the landing page links to `/signup` and `/checker`, and the
Playwright happy path already signs up before it submits.

So a quota was not the first change. Attribution was.

## 3. What shipped

All on `feat/session-25-quota-enforcement`. **No Alembic migration**, by design
— the same reasoning as session 24 — so the deploy is image-only and
`rollback.sh` genuinely covers it. **ADR-45** records the decisions.

**Authentication and attribution.** `POST /api/v1/analyses` requires a bearer
and the `analysis:run` permission (Analyst and above), and stamps the caller's
`org_id`. `GET /api/v1/analyses/{id}` now routes through
`tenancy.readable_analysis` — **its first call site ever** (tech-debt #63, which
recorded that the function and `scoped()` were written and called by nothing).
An org-less row stays world-readable on its unguessable id; an org's row is that
org's alone, and a cross-tenant id gets the same 404 as a missing one.

Stamping `org_id` on a run is not free: the moment an analysis belongs to
somebody, serving it to everybody is a cross-tenant read. The scoping is not a
bonus, it is the other half of the same change.

**Enforcement.** Three allowances, and they are not the same kind of thing:

| Metric | Kind | Where |
|---|---|---|
| `analyses` | flow — events per calendar month | `POST /analyses` |
| `site_audits` | flow | `POST /seo-projects` (only when a crawl is queued) and `POST /{id}/audits` |
| `projects` | **stock** — rows held, not rows created | `POST /seo-projects` |

`projects` needed a new primitive. `UsageCounter` is a monthly window, and Free's
`projects: 1` read through a monthly counter means *one new project per month* —
twelve by December — with deleting one freeing nothing back. `check_stock_quota`
compares the limit against the rows that exist. The plan JSON does not
distinguish flow from stock, so the call site must.

**Money is recorded, not gated.** `reserve()` refuses when the credit balance
cannot cover an estimate. No organization has ever been granted credit, so every
balance is 0 — using `reserve()` on the analysis path would have refused **every
analysis in production** with a 402. Counts gate; the ledger records. The worker
now calls `services/analyses.settle_cost` when a run reaches a terminal state,
**including `failed`** (a run that died in step five still paid for steps one to
four), charging the difference between spend-so-far and what the ledger already
holds so the worker's three retry attempts cannot double-charge. Per-org spend
is visible for the first time — the input P7.8's rollups need. The unusable
credit gate is recorded as tech-debt #74.

**Three refusals, told apart.** `limit_for` used to return `0` for an unseeded
`plans` table, which is fail-closed and correct in direction and
indistinguishable from an exhausted customer. Production ran with an empty
catalog until session 21 caught it; with enforcement live, that would have told
every organization at once that it was out of quota, and the real cause would
have been the last thing anyone checked. `PlanCatalogMissing` is now its own
exception. `api/main.py` registers app-level handlers — `QuotaExceeded` → 429
with `metric`/`used`/`limit`, `InsufficientCredit` → 402, `PlanCatalogMissing`
→ 503 — rather than a try/except per route, because the failure mode of the
per-route form is a future metered path that raises `QuotaExceeded` and returns
500.

**A key for the cage.** `QUOTA_ENFORCEMENT_ENABLED` (default **on**) is read in
exactly one place, `services/quota.py`, so the switch cannot be half-on. And
`scripts/set_org_plan.py` moves an organization to any tier, because there is no
Stripe lifecycle and no back office, and enforcement with no way to lift a limit
is a cage with no key.

**Frontend.** `createAnalysis` and `getAnalysis` go through `authorizedFetch`.
The 429 handling needed care: two limits answer 429 and they ask for opposite
things — "wait a moment" is wrong advice for an allowance that resets next
month — so the plan refusal passes through verbatim and only the rate limiter's
terse `rate limit exceeded` is rewritten.

## 4. The checker, answered rather than skipped

The card names three spend paths and the third is the checker. It is **not**
org-metered, deliberately, and that is a decision rather than an omission: the
checker is the anonymous lead-capture tool, so there is no organization to
charge, and metering a *signed-in* caller for using the free public tool would
bill customers for marketing. Its spend stays bounded globally by machinery that
already exists and is live — `CHECKER_ENABLED`, 10 submits/IP/hour, 20 fresh
runs/brand/day, and `CHECKER_DAILY_USD_CAP` summed over `responses.cost_usd`.

The honest sentence is that the checker is **capped, not metered**, and the two
are different words. Recorded in ADR-45 so the next reader does not find a gap
and assume it was missed.

## 5. What the work found on its own

**A duplicate project was about to become a quota refusal.** On Free, "you
already track this domain" and "you have used your one project" are both true
for the same request, and the guard order decided which the customer was told. A
429 would say *buy more capacity* for a project they already have. `POST
/seo-projects` now answers the 409 first, via an extracted `already_tracked()`;
the service keeps its own check, which is the guarantee, and this is only the
ordering.

**A test that could pass for the wrong reason.** The plan quota and the per-IP
rate limit both answer 429 and both default to 5. The first version of
`test_free_allows_five_analyses_a_month_and_refuses_the_sixth` passed while
asserting nothing about plans — the sixth submit was refused by the rate
limiter. The two suites now make opposite pinning choices and each says why:
`test_rate_limit.py` runs on an unlimited plan, `test_quota_enforcement.py`
lifts the IP limit out of the way. This is the same class of defect session 24
found in the tenancy suite, and it is worth noticing that it recurred within one
session of being written down.

**The test fixtures were describing a deployment that cannot exist.** Every
suite ran against an empty `plans` table while production's is seeded by
migration `0016`. Harmless while nothing read a plan; now it would mean the
whole suite proves that routes work when no limit applies. `conftest.py` seeds
the catalog, so the default test organization is on Free with Free's real
numbers, and a suite that needs headroom says so out loud (`on_plan`,
`signed_in(plan_key=…)`). That is deliberately noisier than a global "unlimited"
default: a test that has to name a tier is a test whose author saw the limit.

## 6. Verified against production before assuming

Two facts were checked on the live database rather than reasoned about, because
both decide whether this change breaks anything that exists.

**Every production analysis has `org_id IS NULL`.** `select count(*),
count(org_id) from analyses` → **57, 0**. So scoping the read route changes the
visibility of exactly zero existing rows: all 57 stay world-readable on their
id, and every link anyone holds keeps working. The backfill was written that way
on purpose — `org_backfill.py` says anonymous rows are never rewritten to point
at the reserved `public` org, because that "would make public rows *look*
owned". That decision from P7.1 is what makes this session's change safe.

**`scripts/set_org_plan.py` was exercised end to end**, not just written: a
scratch Postgres, `alembic upgrade head`, then `--plans` (the seeded catalog
prints), `--list` (both orgs, correctly showing "free (implied — no subscription
row)"), `--set enterprise` by slug, `--set pro` (supersedes the previous
subscription rather than deleting it), the same command twice (idempotent), and
both error paths — an unknown plan key and an unknown org — each exiting 1 with
a readable message. This is the tool the operator runs against production; it
would be a poor thing to ship untried.

## 7. Assumptions recorded

1. **Closing `POST /analyses` to anonymous callers is engineering's call, not
   the operator's.** It is reversible in one line, no product surface uses it,
   and leaving it open would make the quota a control that signing out defeats.
   The operator is told plainly at the head of `operator-expected.md` rather
   than asked, and **B17** gives them the merge decision with the consequence
   spelled out.
2. **The kill switch defaults ON.** Shipping enforcement dark would leave the
   tiers decorative, which is the defect. The switch exists so the operator can
   reverse it from `deploy/.env` without a code change.
3. **Free's numbers are treated as given, not ratified.** 5 analyses, 1 audit,
   1 project were seeded in session 21 as plausible defaults; nobody has
   approved them as pricing. Raised under **A5** rather than changed here.
4. **No Free `Subscription` row is created at signup.** `limit_for` already
   falls back to Free, so it would change no behaviour today while committing
   now to lifecycle semantics (`status`, `current_period_end`) the Stripe card
   should choose.
5. **The concurrency hole in `consume_quota` is accepted for now** (tech-debt
   #75). Two simultaneous submits from one org can both pass a check; worst case
   is one extra unit of a monthly allowance. `SELECT … FOR UPDATE` is the fix
   and it waits until a metered unit is expensive — the backlink vendor adapter
   is the first candidate.

## 8. Loop 2 — B13 was not as operator-owned as it looked

With loop 1 committed, the operator dependency check asked the question the
brief insists on: *is this actually blocked, or merely inconvenient?* The merge
(B17) is genuinely the operator's — it changes what live users can do. **B13 was
not.**

B13 read as one indivisible operator item: "stand up database backups". Split
along the line of who can actually do each part, most of it is engineering:

| Part | Whose |
|---|---|
| Take a dump | engineering |
| Prove the dump is real | engineering |
| Prove it *restores* | engineering |
| Refuse to migrate without one | engineering |
| Choose where an off-box copy lives | **operator** (needs a destination + credential) |
| Install a cron entry on the live box | **operator** |
| Decide the retention window | **operator** (interacts with a PII policy that does not exist) |

Two sessions had steered around a blocker whose first four rows nobody had
built. **ADR-46** records the design; what follows is what it cost and what it
proved.

**`deploy/backup.sh`** takes one `pg_dump --format=custom`, writes it under a
`.partial` name, and renames it into place only after a size floor, a free-space
floor and a full read-back. `0600` in a `0700` directory — a dump is the whole
database in one file, password hashes and audit payloads included. Retention is
count-based (newest 14), because an age rule silently leaves you with nothing if
the schedule stops.

**`deploy/restore-check.sh`** restores a dump into a throwaway container and
asserts the restore exited clean, `alembic_version` holds a revision, and
`users` / `organizations` / `analyses` / `audit_events` exist with their counts
printed. It cannot touch production; there is no flag for it.

**`deploy.sh` now snapshots before a schema change**, comparing `alembic current`
with `alembic heads`, and aborts the deploy if the dump fails — while nothing
has changed and the previous release is still serving. Failing to *determine*
the answer takes the snapshot: the expensive answer is the safe one.

### The check that would have reassured and not protected

The first verification used `pg_restore --list`, which is the obvious choice.
Testing it against a dump truncated to its first 100 KB: **207 TOC entries,
exit 0, passed.** A custom-format archive keeps its table of contents in the
header, so `--list` catches a corrupt header and nothing else — it would have
blessed every half-written file.

`pg_restore --file=/dev/null` decompresses every entry and discards the SQL, so
truncation fails. It costs 1.1s on a 2.7 MB dump. That is the check that
shipped, and the reason the first one was thrown away is written into both the
script and `deploy/BACKUP.md`: a backup check that passes a half-written file is
worse than no check, because it is the reason nobody looks again.

There was a second wrong turn before that one. Piping the dump into a container
on stdin — `pg_restore --list /dev/stdin` — fails with "did not find magic
string in file header" on a **perfect** dump, because reading a custom archive
needs to seek. Had that shipped, the check would have rejected every good
backup. Both mistakes were found by running the thing, not by reading it.

## 9. Rehearsed against the live database

The point of all of it. Run on this box, against production:

```
>> dumping yanki-prod db → ~/yanki-backups/yanki-20260808T235134Z.dump
>> ok: 2.7M, read back in full
>> rehearsing restore of yanki-20260808T235134Z.dump (2.7M)
>> alembic_version = 0018_invitations_audit_integrity
   users: 6 rows        organizations: 7 rows
   analyses: 57 rows    audit_events: 35 rows
>> 30 tables in public schema
>> restore check PASSED
```

2.7 MB dump of a 17 MB database; 65 G free on the disk. Both failure paths were
exercised too — a truncated dump is refused by `pg_restore --exit-on-error`, a
missing dump exits 1 with a message naming where it looked. Retention pruning
was checked by running with `YANKI_BACKUP_KEEP=1` and confirming exactly one
file survived.

The pre-migration detection was checked against the live stack rather than
reasoned about: `alembic current` and `alembic heads` both report
`0018_invitations_audit_integrity`, so a deploy today correctly skips the
snapshot. **The branch that takes one has therefore never run in anger**
(tech-debt #78) — the next migration-bearing deploy is its first real test, and
the deploy log is worth watching rather than walking away from.

`pg_dump` is read-only and the stack was untouched throughout; the only writes
were files in `~/yanki-backups` and two throwaway containers, both removed.

## 10. Loop 3 — the system reported health it had not checked

The operator check again: B17 (merge) and B13's remainder (off-box copy, cron)
are genuinely the operator's; **the last two rows of the backlog's P0 band were
not blocked by anything.** They also turned out to be one defect wearing two
hats. **ADR-47**.

**`/healthz` returned the literal `{"status": "ok"}`.** That is not a health
check; it is a check that uvicorn is accepting sockets. It mattered because it
is the **deploy gate** — `deploy.sh` and `rollback.sh` poll it and write
`.last-good` when it answers — so a release whose database was unreachable, or
(since loop 1) whose plan catalog was empty, reported healthy and was recorded
as *the good release to roll back to*. The gate could not fail.

**The worker had the mirror image.** A `while True` loop with no HTTP surface,
`restart: unless-stopped`, and no healthcheck: a loop that stopped looping left
the container in state `running` and the queue quietly undrained. The only
symptom was jobs sitting in `queued` until a human noticed.

What shipped: `/healthz` is a readiness probe over six components — database,
schema revision, plan catalog, queue, worker, providers — of which **only two
can turn it red**, the database and (with enforcement on) an empty plan catalog.
The worker beats to a file on a volume the api mounts **read-only**, on every
poll and at every pipeline step; a compose healthcheck reads the same file.

### Three judgements worth keeping

**Almost nothing may fail the probe.** A health check that goes red for things
that do not stop the service is one people learn to ignore — and this one
auto-rolls-back a deploy. A queue backlog means customers are using the product.
A missing provider key under `DRY_RUN` is correct. A schema revision differing
from the code's head is *normal during a rollback*, which is precisely when
refusing to serve would be worst. None of those is a reason to reject a release.

**The body is load-bearing in an ugly way.** `deployment.sh` does not trust the
status code — it greps the body for the substrings `status` **and** `ok`. So an
unhealthy body containing "ok" anywhere would pass the gate it exists to fail:
a field named `"ok": false`, a detail mentioning a "token", a message about
something "broken". Component states are `pass`/`fail`/`warn`, the failing state
is `unhealthy`, and a test asserts the unhealthy body contains no "ok" at all.
Pinned rather than hoped for (tech-debt #83 notes it covers one failure path,
not every future one).

**Making the endpoint real also made it a disclosure.** nginx routes `/healthz`
from the internet, and the new breakdown names the schema revision, the queue
depth, whether provider keys are set, and how stale the worker is. Nothing there
is a credential and nothing there should be handed to whoever asks. The public
body carries the **verdict only**; internal callers get the reasons. The verdict
is identical for both, because two gates disagreeing about the same deploy would
be worse than either problem.

### Verified rather than assumed

The healthcheck shell command was run in the real base image (`python:3.12-slim`)
across all three states: fresh heartbeat → exit 0, two-hour-old heartbeat →
exit 1, missing file → exit 1. `docker compose config` renders both compose
files, and `scripts/check_prod_compose.py` still passes on the rendered prod
config, so the caps CI asserts were not disturbed by the new volume.

### The bug my own docstring said could not happen

`health.beat` is documented as "never raises — a heartbeat must not kill a job",
which is load-bearing: it runs inside the pipeline's step loop, so anything it
throws becomes a failed analysis. It caught `OSError`.

Sixteen pipeline tests went red on `AttributeError`. Their settings fixture is a
`SimpleNamespace` mirroring `Settings`, and it has no `worker_heartbeat_path` —
not an `OSError`, so not forgiven. In production the field always exists, so
this would have shipped and waited for the first duck-typed caller.

The lesson is narrower than "add the field to the fixture", which is why both
were done: **a best-effort side effect must not be selective about what it
forgives.** The catch is now `Exception`, with the reason written next to it,
and the fixture points at a temp file so the tests exercise the real path rather
than the fallback.

**One honest limit, stated because it is easy to misread the row as closed.**
Compose — unlike Swarm — **never restarts a container for being unhealthy**. The
healthcheck makes a wedged worker *visible*, in `docker ps` and in `/healthz`.
It does not restart it. Closing that needs an autoheal sidecar (a sixth
container on a shared box, holding the Docker socket) or an external watchdog,
and neither is worth adding blind (tech-debt #81).

## 12. Current state

**Implemented and verified:** everything in §3 (quota enforcement), §8
(backups) and §10 (health). `make test` exit 0 —
**933 backend passed / 7 skipped** with Postgres (the same 7 as the baseline, so
the Postgres-gated suites ran rather than quietly skipping), **327 frontend
across 57 files** — 36 backend tests added across the three loops. `ruff check`, `mypy app` and `npx tsc --noEmit` all clean;

A note on how those numbers were arrived at, because the first three attempts
were wrong. Two `make test` runs overlapped, and `make test` both creates and
`docker rm -f`s the throwaway Postgres by a fixed container name — so the
second run's teardown pulled the database out from under the first, and both
reported **22 skipped** instead of 7. The 15 extra skips were the Postgres-only
suites silently opting out. Worth knowing: a green run with a raised skip count
is not a green run, and nothing in the output says so.

The backup tooling is shell and has no unit tests; it was verified by running
it against the live database and by exercising its failure paths (§9). That is a
deliberate trade — a mocked test of a backup script proves the mock — but it
means the pre-migration branch that has never fired is genuinely unproven
(#78), not merely untested.

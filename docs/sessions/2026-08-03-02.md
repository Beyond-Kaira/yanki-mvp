# Session 17 — 2026-08-03 — standing up the SearXNG instance and turning SERP on

**Branch:** `feat/serp-instance` (off `main` at `a599649`)
**Card:** P5.17 · **ADR:** ADR-29

## 1. What this session was

Session 16 shipped SERP visibility and deliberately did **not** stand up the
instance, because a container on a VPS shared with four other production tenants
costs real resources and that spend is the operator's call. It was written up as
optional item **B6** in `operator-expected.md`.

The operator answered: yes, set it up and turn it on. So this session is the
execution of that decision — an **infrastructure** change, not a feature change.
No SERP feature code was touched.

Measuring first changed several of the parameters, which is most of what is
interesting here.

## 2. What changed

**A profile-gated compose service, not a hand-run container**

`searxng` is now a service in both `deploy/docker-compose.prod.yml` and
`deploy/docker-compose.yml`, behind the `serp` profile. It starts only when
`deploy/.env` carries `COMPOSE_PROFILES=serp` — and because compose reads that
from the project-directory env file, which here *is* `deploy/.env`, opting in
needed **no change to `deployment.sh`**. Anyone else deploying this public repo
never creates a container they did not ask for.

A container that only exists in someone's shell history survives exactly until
the day somebody needs to know it exists.

**No published port, and the limiter off — as one decision**

Prod publishes nothing for it; only `api` and `worker` reach it over the compose
network at `http://searxng:8080`. SearXNG's limiter answers 403 to a bot-shaped
client and Yanki identifies as `YankiBot/0.1`, so with the limiter on every query
would read as unavailable. Turning it off is safe *because* there is no port. The
two must never be changed independently, and both the compose file and the
settings template say so.

**Hard caps, because the box is shared**

`mem_limit: 512m`, `cpus: 0.5`, bounded json-file logs. Measured steady state is
~105–150 MiB. The box had ~3 GB available with Ant Media at 1.1 GB and two
ClickHouse instances beside it; an unbounded search aggregator there is a
neighbour-killer waiting for a slow day.

**The engine set, chosen by measurement rather than by default**

SearXNG enables ten engines in the `general` category. Six of them — currency,
dictzone, lingva, mymemory translated, wikidata, wikipedia — are translation,
currency and encyclopedia widgets that cannot produce an organic commercial
result. They are dropped. The four real web-search engines are kept.

**Config lives on the host, like `deploy/.env`**

`deploy/searxng/settings.yml` is gitignored and symlinked into the auto-deploy
checkout, mirroring the arrangement `deploy/.env` already uses, and for the same
reason: it carries a real `secret_key`, the repo is public, and CI scans full
history with gitleaks. Only `settings.example.yml` is tracked, with SearXNG's own
low-entropy `ultrasecretkey` placeholder.

Worth knowing for whoever debugs this next: the container generates a key **only**
when no settings file exists. A mounted file is used verbatim, nothing is
substituted, so the one-time `sed` on the host is not optional.

## 3. What measuring changed

Three decisions came out different than they would have from reading the docs.

- **Two of the four engines are refused from this egress IP.** Across 8
  buyer-style queries, `google cse` answered 8/8, `duckduckgo` 5/8, and `brave`
  and `startpage` refused 8/8. The obvious move is to narrow the set to the two
  that work — and that would have been wrong: a later probe from inside the
  compose network had `brave` answering and `duckduckgo` refusing. Availability
  is intermittent *per query*, so a set tuned to today's winners is tuned to
  noise. All four stay.
- **`unresponsive_engines` will be non-empty on most rows.** That is accurate
  reporting, not a fault, and it is exactly the field `SerpPage.measurable`
  exists to weigh. It is also the honest admission that the number leans on
  `google cse` more than a four-engine panel suggests (tech-debt #44).
- **`DRY_RUN` forces the mock SERP source**, so the real-search path cannot be
  rehearsed with a mocked LLM panel. Found by trying it. The coupling is
  deliberate — DRY_RUN promises `$0` *and* a reproducible run, and CI's `stack`
  job pins `source == "mock"` — but it conflates "spend no money" with "make no
  network calls", and SERP against an instance you host yourself costs nothing
  (tech-debt #43).

## 4. Cost

**$0 in vendor spend** — the source is our own container and adds no paid call.

The real cost is **~150 MiB of RAM and ~0.3 GB of disk on a shared box**, which
is the thing the operator was actually being asked to approve.

## 5. Verification

Everything below was run before merging, because issue #16 means a failed deploy
cannot roll back.

- **Real engine reliability measured** from this VPS: 8/8 pages measurable,
  20–30 results each.
- **Real-brand validation** through the adapter: Salesforce 4/4, HubSpot 4/4,
  Baykar 3/4 on their own categories, ~0.5 s median per query. Salesforce's own
  site matched at rank 2 by domain; the other hits were third-party pages
  (Gartner and similar) matched by text.
- **No brand leak** in any generated query, on real profiles.
- **The profile mechanism proved from `deploy/.env`**, not assumed: without
  `COMPOSE_PROFILES` compose resolves `api db web worker`; with it, `searxng`
  appears. Caps parse (`mem_limit` 536870912, `cpus` 0.5), no ports.
- **A full rehearsal of the exact prod compose file** under an isolated project
  name: all five containers up, and the worker reached the instance over the
  compose network and detected Salesforce at rank 6.
- **The symlinked settings file resolves through a bind mount** from the
  auto-deploy checkout — the one thing that would have failed only in production.
- Production `deploy/.env` was backed up before editing, and is still gitignored.

# Session 16 — 2026-08-03 — SERP visibility from an open-source metasearch source

**Branch:** `feat/serp-visibility` (off `main` at `df35e87`)
**Card:** P5.16 · **ADR:** ADR-28

---

## 1. What this session was

The operator asked for an **open-source SERP database** to be integrated into the
app, with the workflows proven green and new workflows covering the feature,
before opening a PR.

The repo already named the gap this fills. `docs/roadmap.md` lists, under
**Later**: *"Google AI Overviews tracking — our biggest admitted gap vs Semrush;
needs SERP scraping or a paid SERP API."* Both options in that sentence cost
something the product cannot afford to spend. A commercial SERP API bills per
query, which puts a per-analysis invoice in front of the "affordable" wedge and —
worse for a product whose whole pitch is showing its work — makes the number
unauditable, because we could not publish how it was obtained. Scraping the
engines ourselves is a blocklist maintenance treadmill against parties actively
trying to stop us.

There is a third option that sentence predates: **SearXNG** (AGPL-3.0), an
open-source metasearch engine that puts the public engines behind one
self-hostable JSON API. The operator runs a container; we read it. $0, auditable,
and no vendor.

The design question that turned out to matter most was not "how do we read a
SERP". It was **what we are entitled to conclude from one** — which is the same
question ADR-26 and ADR-27 asked of the crawl and the profile.

## 2. What changed

**A `serp/` package, mirroring `providers/` (`app/serp/`)**

- `base.py` — one `SerpSource` protocol with one `search(query)` call, plus
  `SerpResult`, `SerpPage` and `SerpUnavailable`. It is a sibling of
  `providers/` rather than a member because the return value is ranked results
  and *reliability evidence*, not text and a cost.
- `searxng.py` — the adapter. Every field is read defensively; the response
  shape was verified against a **live 2026.8 instance**, not the docs, which do
  not publish a schema. Two things only a live instance tells you:
  `number_of_results` comes back `null`, and `unresponsive_engines` is a list of
  `[name, reason]` pairs.
- `mock.py` — the deterministic DRY_RUN source. Same sha256 trick and same
  roughly-half hit rate as `providers/mock.py`, and about the same fictional
  company, so a DRY_RUN run stays one coherent fiction at $0 with no packets.
- `registry.py` — allowed to return `None`, unlike the provider registry: SERP is
  an extra surface that needs infrastructure no environment has until somebody
  stands it up.

**The measurement (`pipeline/serp_visibility.py`)**

- Queries are built from `prompts.topic_pool` — literally the same brand-free
  pool the scored questions come from — and each finished query is re-checked
  with `prompts.leaks_brand`. ADR-27's invariant on the other surface, and the
  temptation is stronger here because "brand + category" is the obvious thing an
  SEO tool would type.
- Query shapes are keyword-shaped (`best {topic}`, `{topic} comparison`) rather
  than the questions `prompts.py` builds. People type keywords into a search box
  and ask an assistant a question; feeding a search engine the question form
  measures how well it handles questions, which is not the thing under test.
- A hit is a **domain match or a text match**. A result is mostly a URL and two
  lines of snippet, so the company's own site ranking is the strongest available
  signal and needs no text at all — which makes this the one place in the
  pipeline that can see a company the LLM panel never names. A listicle naming it
  in the snippet counts too, through the same `footprint.detect` the panel uses.
- It runs **inside the footprint step**, not as a seventh one. Footprint is the
  step that asks where the brand appears; this asks it of a second corpus.
  `current_step`, the progress mapping and `StepProgress` are untouched.

**The honesty rule, which is the point of the whole feature**

A live SearXNG answers `200 OK` with an empty result list when its upstream
engines rate-limit or CAPTCHA it. This is not a rare edge — measured on an
ordinary query during this session, `brave`, `duckduckgo`, `startpage` and
`wikipedia` were *all* refused at once. Reading that page as "the brand ranks
nowhere" would manufacture a zero out of a failed measurement.

So: `SerpPage` carries `unresponsive_engines`, `measurable` refuses to call an
empty page from a broken panel evidence of absence, unmeasurable queries are
dropped from the denominator rather than counted as misses, and `serp_score`
returns `None` — not `0.0` — when nothing could be measured. Three different
nulls with three different meanings, all the way out to the UI:

| What the user sees | What it means |
|---|---|
| no SERP section at all | the run never measured (feature off, or an older row) |
| "we could not read search results" | we looked and could not see |
| `0%` | we read them, and the brand was in none |

**Persistence, contract, UI**

- `serp_checks` (one row per query) stores the evidence — which query, which
  result, at what rank, and which engines refused. Stored rather than
  recomputed: the wedge is showing our work, and a SERP is a snapshot of
  something that moves.
- Five nullable `serp_*` columns on `analyses`, migration `0007`, additive, with
  **no** server defaults — backfilling them to 0 would claim we looked.
- `ResultOut` gains a nullable `serp` object, so `make gen-types` is a real diff.
  `checker_methodology.json` is untouched (`gen_methodology.py` never imports the
  API schemas).
- `SerpVisibility.tsx` on both results pages, with the not-measured state
  rendered as a sentence rather than as an empty bar.

**One refactor, no duplication**

`prompts._brand_keys` / `_leaks_brand` became public `brand_keys` / `leaks_brand`
so query generation reuses the brand filter instead of copying it. ADR-26 already
rejected keeping a second copy of a shared table (the fold map), for the reason
that applies here too: two copies drift, and the two things that would drift are
"is this the brand" in a prompt and "is this the brand" in a query.

## 3. Assumptions recorded

- **SearXNG is the right open-source source.** It is the only mature project that
  federates the engines that matter behind a self-hostable JSON API. If it dies,
  the `SerpSource` protocol is one file to reimplement.
- **The instance URL is operator config, not user input**, so it deliberately
  gets **no** `net_guard` SSRF check. `net_guard` exists because discovery
  fetches a URL a stranger submitted; the intended deployment here is
  `http://searxng:8080` on the compose network, which is exactly the private
  space the guard rejects. Guarding it would break every correct deployment to
  protect against somebody who already sets `DATABASE_URL`.
- **Rank is the index in the merged list**, not the per-engine `positions` array,
  which cannot be compared across a metasearch page.
- **`serp_query_count` (6) is a politeness budget chosen by reasoning, not
  measurement.** Each query is one HTTP call to the operator's own instance, so
  there is no vendor cost signal to tune against (tech-debt).

## 4. Cost

**$0.** The feature adds no paid call — the source is the operator's own
container, and DRY_RUN uses a deterministic mock that never opens a socket. The
existing per-run LLM spend is unchanged; SERP adds no provider traffic.

## 5. Verification

Everything below was run, not assumed.

- **Against a real SearXNG**, twice. First a plain instance, to capture the true
  JSON shape (which is where the `null` `number_of_results` and the four refused
  engines were found). Then the CI configuration end to end: 7/7 integration
  tests green against `searxng/searxng:2026.8.1-8892414dc`, federating only the
  fixture engine.
- **The unmeasurable path proved against real SearXNG, not a mock of it.** The
  fixture engine can be made to error on demand, and the instance then does
  exactly what it does when Brave rate-limits it: `results: 0`,
  `unresponsive_engines: [['fixture', 'HTTP error']]`. The test asserts that page
  is not scoreable.
- **The migration on real Postgres**: `upgrade head` → schema present →
  `downgrade -1` → schema absent → `upgrade head` → present. CI had never run
  alembic at all before this session; the new `migration` job now does.
- **A whole analysis through the compose stack** with `SERP_ENABLED=1`: measured
  2/4 with 4 evidence rows, score exactly `hits/queries`, and no generated query
  naming the brand. The generated queries on the DRY_RUN profile read
  `best AI visibility tools`, `best brand visibility tracking in Istanbul`,
  `top AI answer monitoring companies`, `analytics comparison`.
- **`SERP_ENABLED` reaching the worker** through the same `env_file` path the CI
  stack job uses, confirmed by running the built worker image against it.
- 383 backend tests green the way CI runs them (380 + the three real-Postgres
  queue tests; 7 skipped are the SERP integration tier, which needs a live
  instance) and 79 frontend tests; `ruff check`, `mypy`, `tsc`,
  `eslint` clean; `make gen-types` reproduces the committed contract exactly;
  `actionlint` clean on all four workflows; `gitleaks` finds nothing in any
  tracked file.
- **An adversarial review of the finished branch** (four independent lenses:
  correctness, the design invariants, CI, and security/data) found one real
  defect the test suite had not: a re-run of an analysis after SERP was switched
  off deleted the `serp_checks` rows but left the summary columns behind, so the
  API would have served a score with an empty evidence table under it — precisely
  the "number with no working shown" this feature is organised against. The
  summary is now cleared in the same place as the evidence it summarises, and a
  regression test pins it. Two further findings were recorded as debt rather than
  fixed (#41 IDN host forms, #42 no byte cap on the response); the rest were
  refuted or were confirmations that a deliberate choice was sound.
- Two things this session's tests **caught in my own code**: a checker run's
  synthetic `checker://<brand>` URL was being parsed as a hostname (so a search
  result served from a host of that name would have been credited as the
  company's own site), and `run_serp` originally caught only `SerpUnavailable`,
  which did not honour the fail-open promise the ADR makes. Both fixed, both
  pinned by a test.

## 6. Current state

- **Implemented:** the source package, the pipeline pass, persistence, the API
  contract, the UI, the test suite, and a new `SERP` workflow.
- **Incomplete by design:** Google AI **Overviews** specifically — the AI answer
  box on a Google results page — is a different artifact from the organic
  results SearXNG federates, and is still open. Position weighting, scheduled
  re-measurement (rank tracking over time), and a production SearXNG instance are
  all deliberately not in this slice.
- **Off by default.** `SERP_ENABLED=0` everywhere. Nothing changes for the live
  deployment on merge until an operator turns it on *and* stands up an instance —
  see `operator-expected.md`.
- **Blockers:** none. **Merging to `main` auto-deploys to production**, and this
  change is inert there until the operator acts.
- **Contract impact:** `openapi.json` + `types.ts` change (new nullable `serp`
  object). Migration `0007` is additive and reverts cleanly.

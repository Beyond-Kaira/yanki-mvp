## 2. The card was blocked by something no document mentioned

`enforce-quota-on-spend-paths` reads like a wiring job: `services/billing` has
`check_quota`, `consume_quota`, `reserve`, `settle`; three routes need to call
them. Reading the code first — the standing instruction, earning its place a
fifth time — found the actual blocker.

**`POST /api/v1/analyses` took no authentication.** Not a permission gap, not a
weak check: no credential of any kind. Which meant:

- every analysis a paying customer ran carried `org_id = NULL`;
- it belonged to no organization, appeared in no organization's history, and
  could be metered against **nothing**;
- anyone could spend money at a paid vendor through it, bounded only by the
  per-IP rate limit.

It is a leftover, not a decision. `/` used to *be* the analysis form; session 21
made `/` a landing page and moved the form behind sign-in, and nobody closed the
route the form posts to. The evidence that closing it breaks nothing is
mechanical: every caller of `createAnalysis` sits inside `RequireAuth`
(`/dashboard`, `/ai-visibility`, `/search-visibility`, the analysis-bound
subpages), the landing page links to `/signup` and `/checker`, and the
Playwright happy path already signs up before it submits.

So a quota was not the first change. Attribution was.

## 3. What shipped

All on `feat/session-25-quota-enforcement`. **No Alembic migration**, by design
— the same reasoning as session 24 — so the deploy is image-only and
`rollback.sh` genuinely covers it. **ADR-45** records the decisions.

**Authentication and attribution.** `POST /api/v1/analyses` requires a bearer
and the `analysis:run` permission (Analyst and above), and stamps the caller's
`org_id`. `GET /api/v1/analyses/{id}` now routes through
`tenancy.readable_analysis` — **its first call site ever** (tech-debt #63, which
recorded that the function and `scoped()` were written and called by nothing).
An org-less row stays world-readable on its unguessable id; an org's row is that
org's alone, and a cross-tenant id gets the same 404 as a missing one.

Stamping `org_id` on a run is not free: the moment an analysis belongs to
somebody, serving it to everybody is a cross-tenant read. The scoping is not a
bonus, it is the other half of the same change.

**Enforcement.** Three allowances, and they are not the same kind of thing:

| Metric | Kind | Where |
|---|---|---|
| `analyses` | flow — events per calendar month | `POST /analyses` |
| `site_audits` | flow | `POST /seo-projects` (only when a crawl is queued) and `POST /{id}/audits` |
| `projects` | **stock** — rows held, not rows created | `POST /seo-projects` |

`projects` needed a new primitive. `UsageCounter` is a monthly window, and Free's
`projects: 1` read through a monthly counter means *one new project per month* —
twelve by December — with deleting one freeing nothing back. `check_stock_quota`
compares the limit against the rows that exist. The plan JSON does not
distinguish flow from stock, so the call site must.

**Money is recorded, not gated.** `reserve()` refuses when the credit balance
cannot cover an estimate. No organization has ever been granted credit, so every
balance is 0 — using `reserve()` on the analysis path would have refused **every
analysis in production** with a 402. Counts gate; the ledger records. The worker
now calls `services/analyses.settle_cost` when a run reaches a terminal state,
**including `failed`** (a run that died in step five still paid for steps one to
four), charging the difference between spend-so-far and what the ledger already
holds so the worker's three retry attempts cannot double-charge. Per-org spend
is visible for the first time — the input P7.8's rollups need. The unusable
credit gate is recorded as tech-debt #74.

**Three refusals, told apart.** `limit_for` used to return `0` for an unseeded
`plans` table, which is fail-closed and correct in direction and
indistinguishable from an exhausted customer. Production ran with an empty
catalog until session 21 caught it; with enforcement live, that would have told
every organization at once that it was out of quota, and the real cause would
have been the last thing anyone checked. `PlanCatalogMissing` is now its own
exception. `api/main.py` registers app-level handlers — `QuotaExceeded` → 429
with `metric`/`used`/`limit`, `InsufficientCredit` → 402, `PlanCatalogMissing`
→ 503 — rather than a try/except per route, because the failure mode of the
per-route form is a future metered path that raises `QuotaExceeded` and returns
500.

**A key for the cage.** `QUOTA_ENFORCEMENT_ENABLED` (default **on**) is read in
exactly one place, `services/quota.py`, so the switch cannot be half-on. And
`scripts/set_org_plan.py` moves an organization to any tier, because there is no
Stripe lifecycle and no back office, and enforcement with no way to lift a limit
is a cage with no key.

**Frontend.** `createAnalysis` and `getAnalysis` go through `authorizedFetch`.
The 429 handling needed care: two limits answer 429 and they ask for opposite
things — "wait a moment" is wrong advice for an allowance that resets next
month — so the plan refusal passes through verbatim and only the rate limiter's
terse `rate limit exceeded` is rewritten.

## 4. The checker, answered rather than skipped

The card names three spend paths and the third is the checker. It is **not**
org-metered, deliberately, and that is a decision rather than an omission: the
checker is the anonymous lead-capture tool, so there is no organization to
charge, and metering a *signed-in* caller for using the free public tool would
bill customers for marketing. Its spend stays bounded globally by machinery that
already exists and is live — `CHECKER_ENABLED`, 10 submits/IP/hour, 20 fresh
runs/brand/day, and `CHECKER_DAILY_USD_CAP` summed over `responses.cost_usd`.

The honest sentence is that the checker is **capped, not metered**, and the two
are different words. Recorded in ADR-45 so the next reader does not find a gap
and assume it was missed.

## 5. What the work found on its own

**A duplicate project was about to become a quota refusal.** On Free, "you
already track this domain" and "you have used your one project" are both true
for the same request, and the guard order decided which the customer was told. A
429 would say *buy more capacity* for a project they already have. `POST
/seo-projects` now answers the 409 first, via an extracted `already_tracked()`;
the service keeps its own check, which is the guarantee, and this is only the
ordering.

**A test that could pass for the wrong reason.** The plan quota and the per-IP
rate limit both answer 429 and both default to 5. The first version of
`test_free_allows_five_analyses_a_month_and_refuses_the_sixth` passed while
asserting nothing about plans — the sixth submit was refused by the rate
limiter. The two suites now make opposite pinning choices and each says why:
`test_rate_limit.py` runs on an unlimited plan, `test_quota_enforcement.py`
lifts the IP limit out of the way. This is the same class of defect session 24
found in the tenancy suite, and it is worth noticing that it recurred within one
session of being written down.

**The test fixtures were describing a deployment that cannot exist.** Every
suite ran against an empty `plans` table while production's is seeded by
migration `0016`. Harmless while nothing read a plan; now it would mean the
whole suite proves that routes work when no limit applies. `conftest.py` seeds
the catalog, so the default test organization is on Free with Free's real
numbers, and a suite that needs headroom says so out loud (`on_plan`,
`signed_in(plan_key=…)`). That is deliberately noisier than a global "unlimited"
default: a test that has to name a tier is a test whose author saw the limit.

## 6. Verified against production before assuming

Two facts were checked on the live database rather than reasoned about, because
both decide whether this change breaks anything that exists.

**Every production analysis has `org_id IS NULL`.** `select count(*),
count(org_id) from analyses` → **57, 0**. So scoping the read route changes the
visibility of exactly zero existing rows: all 57 stay world-readable on their
id, and every link anyone holds keeps working. The backfill was written that way
on purpose — `org_backfill.py` says anonymous rows are never rewritten to point
at the reserved `public` org, because that "would make public rows *look*
owned". That decision from P7.1 is what makes this session's change safe.

**`scripts/set_org_plan.py` was exercised end to end**, not just written: a
scratch Postgres, `alembic upgrade head`, then `--plans` (the seeded catalog
prints), `--list` (both orgs, correctly showing "free (implied — no subscription
row)"), `--set enterprise` by slug, `--set pro` (supersedes the previous
subscription rather than deleting it), the same command twice (idempotent), and
both error paths — an unknown plan key and an unknown org — each exiting 1 with
a readable message. This is the tool the operator runs against production; it
would be a poor thing to ship untried.

## 7. Assumptions recorded

1. **Closing `POST /analyses` to anonymous callers is engineering's call, not
   the operator's.** It is reversible in one line, no product surface uses it,
   and leaving it open would make the quota a control that signing out defeats.
   The operator is told plainly at the head of `operator-expected.md` rather
   than asked, and **B17** gives them the merge decision with the consequence
   spelled out.
2. **The kill switch defaults ON.** Shipping enforcement dark would leave the
   tiers decorative, which is the defect. The switch exists so the operator can
   reverse it from `deploy/.env` without a code change.
3. **Free's numbers are treated as given, not ratified.** 5 analyses, 1 audit,
   1 project were seeded in session 21 as plausible defaults; nobody has
   approved them as pricing. Raised under **A5** rather than changed here.
4. **No Free `Subscription` row is created at signup.** `limit_for` already
   falls back to Free, so it would change no behaviour today while committing
   now to lifecycle semantics (`status`, `current_period_end`) the Stripe card
   should choose.
5. **The concurrency hole in `consume_quota` is accepted for now** (tech-debt
   #75). Two simultaneous submits from one org can both pass a check; worst case
   is one extra unit of a monthly allowance. `SELECT … FOR UPDATE` is the fix
   and it waits until a metered unit is expensive — the backlink vendor adapter
   is the first candidate.

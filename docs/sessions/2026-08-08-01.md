## 2. The order question, and why this is not a reordering

The brief fixes the milestone order and says it is not the orchestrator's to
change: Admin Panel first. The backlog puts a Priority-0 band of production-risk
infrastructure ahead of the M1 features. Those look like they conflict. They do
not, and the resolution is the shape of this session.

A5–A8 each add a migration to the live database. **There are no database
backups.** `rollback.sh` restores the image, never the data. So the sequencing
is not "infra instead of the milestone", it is "the milestone's own
prerequisites first": harden the deploy path, then advance A5 through the half
that needs **no migration at all**. Password reset and MFA — the migration-
bearing half — are deferred to a session after backups exist (operator **B13**).

Four lanes, built in parallel in isolated worktrees, each adversarially
reviewed.

## 3. What shipped

All on `feat/session-24`, **unmerged**. No Alembic migration anywhere in it, by
design, so the deploy is image-only and `rollback.sh` genuinely covers it.

**S24-1 — bound the shared-VPS blast radius** (`6404b5b`). Only `searxng` had a
memory cap and a bounded log driver; `db`, `api`, `worker` and `web` had
neither, on a box shared with four other companies' production stacks. Ceilings
derived from measured RSS with 8–17× headroom (db 1g, api 1g, web 768m, worker
1.5g), plus a 10 MiB × 3 log bound on each. Total ceilings: 4.75 GiB of 11.68,
5.0 cores of 6. **ADR-41.**

**S24-2 — make the deploy preflight and rollback survive Phase 7** (`bd3633c`).
`check_env.py` was validating the *retired* four-engine provider keys, so a
deploy missing `OPEN_ROUTER_KEY` passed preflight green and then every job died
at runtime; it now checks what the live path actually reads, traced from
`config.py` and `execute_measured.py`. `rollback.sh`'s pruned-image branch could
check out a pre-`56c1fac` SHA, resurrect the fused `alembic upgrade head &&
uvicorn` command and crash-loop production *during a rollback*; it now refuses
that SHA with a hand-recovery message and restores the branch it started on.
**ADR-42**, repaying most of tech-debt #17.

**S24-3 — P7.5's migration-free half** (`b0b4bec`). `GET /auth/sessions`,
`DELETE /auth/sessions/{id}`, `POST /auth/sessions/revoke-all` — all
self-scoped, all audited — a Devices & sessions section in `/settings`, the
caller's organization list added **additively** to `/auth/me`, and an org
switcher in the shell. **ADR-43.**

This closes a live defect rather than adding a nicety. Invitations shipped in
session 22, so a user can now hold two memberships — but `/auth/me` returned one
org and `resolve_org_context` silently picked `memberships[0]`, so **an accepted
invitation to a second organization was unreachable**. The builder also
corrected the card's own premise: the brief said to extend "the `X-Org-Id` the
API client already sends", and the client had never sent it anywhere. The seam
was honoured server-side and no client code carried it.

**S24-4 — close the Site Audit void** (`1d02333`, corrected in `58af821`).
`SITE_AUDIT_ENABLED`, default off, gating the crawl. **ADR-44.**

The card's premise turned out to be stale in the direction that matters. The
backlog said both tables held zero rows — "a trap that has not yet been sprung."
Production held **three projects and three audits, all `queued` with zero pages
since 2026-08-05/06**. The trap had been sprung; nobody noticed because a queued
row looks like progress. The rows are untouched — mutating production data is an
operator action, especially with no backups (operator **B15**, tech-debt #64).

## 4. What the adversarial reviews caught

Each lane was reviewed by an independent agent reading the diff against `main`.
Three findings survived verification, and the pattern in them is worth keeping.

**A gate that blessed what it claimed to catch** (minor, S24-1). The new CI job
ran `docker compose config -q`, and its own comment claimed this caught "a
swarm-only limit form that a plain `docker compose up` silently drops". It does
not — `config -q` exits 0 on `deploy.resources.limits` exactly as on the
top-level form. The gate would have blessed a compose file whose caps enforce
nothing, which is worse than no gate because it makes a reviewer stop looking.
`scripts/check_prod_compose.py` now asserts the caps against the **rendered**
config, and was tested against all four failure modes before being wired in.

**A sign-out that did not say it signed you out** (nit, S24-3). `revoke-all`
returns `kept_current: false` when it cannot identify the caller's own family —
meaning it revoked everything, this device included. The API was honest; the UI
threw the field away and reported "Signed out 2 other sessions."

**One feature's kill-switch disabling another** (major, S24-4). The gate had
been applied to `POST /seo-projects` as well as to the audits route — and
`SeoProject` is not a Site Audit concept, it is the shared entity **Backlinks
hangs off**. The moment the operator turned Backlinks on (M2, the nearer-term
revenue path) while Site Audit correctly stayed off, no customer could create a
project to attach a backlink profile to.

The builder and the reviewer each had half of this. The builder was right that
project creation queues a crawl and is the path all three stranded rows took;
the reviewer was right that gating it couples two independent features. Neither
proposed the resolution, which is that **the seam is not the route, it is the
crawl**: `create_project_with_audit` gained `queue_audit=`, project creation
stays open, and only the `SiteAudit` row is suppressed.

## 5. The failure that only integration could find

With all four lanes merged, the full suite went red on one test —
`test_reading_another_tenants_audit_is_refused`. With the kill-switch defaulting
off, no first crawl is queued, `latest_audit` is null, and there is no audit id
to read.

The failure was the harmless half. One test up,
`test_queueing_an_audit_on_another_tenants_project_is_refused` **kept passing** —
and its 404 was now the flag refusing everybody rather than the org check
refusing Bob. It would have gone on passing if tenant isolation broke tomorrow.
A leakage test that passes for the wrong reason is worse than one that fails,
because only the failing one asks to be looked at. Fixed in `f546924` by turning
the feature on for that suite: it is a tenancy suite, and the kill-switch has
its own coverage where it belongs.

This is the argument for integrating and re-running rather than trusting four
green lanes.

## 6. Assumptions recorded

1. **P0 infrastructure precedes A5–A8 migrations.** Not a reordering of the
   milestone; a judgement that a migration to an unbackacked live database
   behind a rollback that can crash-loop is not a risk worth taking for speed.
2. **Resource ceilings are derived from a single spot measurement**, not a load
   peak — there is no monitoring history on this box. Headroom is deliberately
   8–17× because of that (tech-debt in ADR-41's consequences).
3. **"Sign out everywhere" keeps the current session**, on the reasoning in
   ADR-43. The service supports the stricter form if the posture changes.
4. **The Support-impersonation conflict was not resolved by engineering.** The
   plan doc and the code disagree; it is an operator decision (**B16**).
5. **The three stranded production audits were left alone.** Cleanup is an
   operator action and should follow backups, not precede them.
